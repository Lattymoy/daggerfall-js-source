# DFO — World Generation 2.0, Settlement System 2.0 & World Editor

## Technical Design & Development Specification

**Project:** DFO Online  
**Status:** Development Specification  
**Primary Inspiration:** Star Citizen's Genesis, Planet Tech and Starchitect concepts  
**Target Platform:** Browser-first, WebGL2, JavaScript, existing multiplayer infrastructure

---

# 1. Executive Summary

The objective is to transform DFO's world generation into a unified, extensible system capable of producing geographically coherent, visually diverse, realistic fantasy environments throughout Tamriel.

The new system must support:

- Large-scale procedural terrain generation.
- Realistic geological formations and erosion.
- Integrated hydrology, climate, soils and ecosystems.
- Region-specific vegetation, terrain materials and natural features.
- Procedural generation of believable settlements.
- Fully custom, handcrafted cities and landmarks.
- A visual World Editor for modifying both generated and existing environments.
- Seamless integration with existing gameplay systems.
- Deterministic multiplayer world generation.
- Preservation of existing player property and persistent world state.

The system must not simply generate attractive terrain. It must produce a **coherent world in which geography, natural resources, infrastructure, settlements and gameplay are interconnected**.

### Core Design Principle

**The world should be generated from interconnected environmental rules, not assembled from unrelated random objects.**

For example:

A mountain range influences rainfall and drainage. Drainage creates river valleys. Water availability influences vegetation and soil fertility. These conditions influence settlement locations, agricultural land, roads and trade routes.

Every subsequent system should use information generated by the previous systems.

# 3. Unified World Architecture

## 3.1 World Data Model

Introduce a unified, versioned world data architecture with the following logical layers:

1. **Canonical Geography** — continents, coastlines, province boundaries, major mountain ranges and lore-defined landmarks.
2. **Generated Environment** — terrain, geology, hydrology, climate, soil and biome data.
3. **Authored World Overrides** — developer-authored adjustments to geography and environmental features.
4. **Settlement & Infrastructure Layer** — cities, villages, roads, bridges, buildings and structural terrain modifications.
5. **Persistent Gameplay Layer** — player property, objects, world events, harvestable resources and other mutable gameplay state.

Each layer must have a clearly defined responsibility, version, ownership and conflict-resolution policy.

An authored override must not silently corrupt or replace unrelated data in other layers.

## 3.2 Canonical World Definition

The geography of Tamriel is not supposed to be completely random.

The following must remain geographically and lore-consistent:

- Province locations and boundaries.
- Major coastlines and islands.
- Important mountain ranges.
- Major rivers and lakes.
- Canonical cities and landmarks.
- Major roads and historically significant locations.

Procedural generation determines the **detailed environment between these constraints**.

For example, Skyrim's mountain ranges must appear in their appropriate locations, but their individual cliffs, valleys, ridges and geological details can be generated procedurally.

## 3.3 World Coordinates and Spatial Partitioning

The new system must support arbitrary positions within the existing world coordinate framework without requiring every object to belong to an RMB block.

Requirements:

- Support freeform settlement footprints and structures.
- Support multiple independently addressable locations within one legacy map pixel.
- Preserve existing map IDs and legacy location lookups.
- Use stable, globally unique entity identifiers for new persistent content.
- Use spatial indexing for efficient queries.
- Use camera-relative or equivalent precision management for large coordinates.
- Allow independently streamable world chunks.

Rendering chunks must not determine the identities of persistent gameplay entities.

A chunk can be regenerated, split or merged without changing the identity of a house, bridge or quest location.

## 3.4 Deterministic Generation

All clients connected to the same world revision must produce identical gameplay-relevant terrain.

Generation must depend on explicitly versioned inputs:

- World seed.
- Geography version.
- Generator version.
- Environmental data version.
- Authored edit revision.
- Settlement data revision.

Generation must not depend on nondeterministic runtime behavior.

Gameplay-relevant collision, elevation and placement data must have reproducible results across supported environments.

Visual-only details may use client-specific quality settings without changing gameplay geometry.

Existing world revisions must remain reproducible after generator updates.

# 4. World Generation 2.0

## 4.1 Geological Generation

Replace the current reliance on noise-dominated local terrain variation with a hierarchical geological model.

The generator must support the following formations:

- Mountain ranges and connected ridgelines.
- Valleys and foothills.
- Plateaus and mesas.
- Cliffs and escarpments.
- Canyons and gorges.
- Rolling hills and plains.
- Coastal cliffs and beaches.
- Dunes and desert basins.
- Volcanic terrain and lava fields.
- Wetlands and lowland depressions.

Geological regions should contain information about rock types, landform characteristics and erosion resistance.

Large-scale geological structures must guide smaller-scale terrain features.

Mountains must resemble connected geological formations rather than isolated cones produced by noise.

### Multi-scale generation

Terrain generation must operate at several scales:

**Continental:** major topography, mountain ranges, basins and coastlines.

**Regional:** valleys, watersheds, hills and major landform structures.

**Local:** slopes, ridges, gullies, rock outcrops and smaller terrain features.

**Surface:** soil variation, stones, cracks, vegetation patches and decorative details.

These scales must connect naturally without abrupt transitions.

## 4.2 Erosion Simulation

Introduce erosion-informed terrain generation.

Support:

- Hydraulic erosion.
- Thermal erosion and slope relaxation.
- Sediment transport and deposition.
- River incision.
- Alluvial deposits.
- Differential erosion based on geological materials.

The objective is believable terrain, not necessarily a physically exact geological simulation.

Expensive erosion operations should be performed during offline or server-side world preparation.

Normal browser clients must not simulate regional erosion when loading terrain.

Deterministic precomputed erosion data must be used to reproduce results.

## 4.3 Hydrology

Build upon the existing Tamriel water systems.

Introduce a unified drainage and watershed model.

Requirements:

- Rivers originate from plausible water sources.
- River networks follow connected drainage systems.
- Tributaries join larger waterways.
- River width and depth vary along their course.
- Lakes form in appropriate basins.
- Waterfalls and rapids appear where elevation changes justify them.
- Wetlands form in suitable low-gradient environments.
- Riverbanks and floodplains are generated from surrounding terrain.
- Groundwater and water availability influence vegetation and settlements.

Terrain geometry must be carved to accommodate water.

Rivers must not appear as flat textures painted over unrelated hills.

Water sources, surfaces, beds, banks and crossings must use coherent elevation information.

Existing water simulation and rendering systems should be extended rather than duplicated.

## 4.4 Climate Simulation

Introduce environmental fields for:

- Temperature.
- Precipitation.
- Humidity.
- Elevation.
- Wind exposure.
- Solar exposure.
- Seasonal variation.

Account for large-scale geographical effects, including:

- Mountain rain shadows.
- Temperature variation with elevation.
- Coastal humidity.
- Dry inland regions.
- Cold northern environments.
- Local microclimates.

These fields guide biome selection and environmental generation.

The climate model must respect established Tamriel lore.

Lore-defined climate differences may override physically predicted climate values.

## 4.5 Soil Generation

Introduce a soil layer describing:

- Soil type.
- Soil depth.
- Moisture retention.
- Fertility.
- Drainage.
- Erosion susceptibility.
- Rock exposure.

Soil data must influence vegetation, agriculture and settlement suitability.

Examples:

- River floodplains produce fertile agricultural land.
- Steep rocky slopes support limited vegetation.
- Poorly drained lowlands become wetlands.
- Arid plains support sparse vegetation except near water sources.

Soil generation must be data-driven and configurable per biome.

## 4.6 Biome and Ecosystem Generation

Extend the existing Tamriel biome system into an environmental simulation model.

Biomes must be determined using environmental data rather than only province or climate categories.

The system must support:

- Forests.
- Grasslands.
- Deserts.
- Tundra.
- Alpine environments.
- Wetlands.
- Tropical and temperate jungles.
- Volcanic environments.
- Coastal ecosystems.

Each biome defines a species and environmental profile.

### Vegetation placement

Vegetation placement must consider:

- Species-specific temperature tolerance.
- Soil requirements.
- Moisture availability.
- Elevation.
- Slope.
- Sunlight.
- Competition and vegetation density.
- Proximity to water.

Vegetation must form natural patterns such as forest clusters, clearings, riparian corridors and ecological transitions.

Avoid uniform distributions of trees and other objects.

### Ecosystem integration

The generated environment must provide data to existing and future gameplay systems:

- Wildlife habitats.
- Enemy habitats.
- Harvestable plants.
- Wood resources.
- Mining deposits.
- Hunting areas.
- Fishing locations.
- Agricultural suitability.

The generator must not replace existing gameplay spawn rules without explicit integration.

# 5. Terrain Rendering and Streaming

The new system must remain compatible with the browser-first WebGL2 renderer.

## 5.1 Terrain LOD

Support continuous terrain loading at different levels of detail.

Requirements:

- High-detail terrain near the player.
- Reduced-detail geometry at medium distances.
- Low-cost distant terrain and mountain silhouettes.
- Smooth transitions between LODs.
- Correct stitching between adjacent chunks.
- Stable terrain silhouettes across rendering distances.

Procedural terrain details must not cause large geometry changes when approaching distant areas.

## 5.2 Terrain Materials

Introduce a data-driven terrain material system.

Materials must support:

- Regional rock and soil types.
- Sand, gravel, mud and grass.
- Wet surfaces.
- Snow and ice.
- Volcanic ash.
- Natural material transitions.

Material distribution must consider slope, elevation, moisture, geological type and biome.

Use texture blending and detail variation to reduce visible repetition.

The renderer must provide configurable quality levels.

## 5.3 Performance Requirements

The system must prioritize browser performance.

Requirements:

- Expensive generation must run outside the main rendering thread.
- Terrain chunks must be cached.
- Streaming must prioritize player position and movement direction.
- Distant details must use appropriate impostors, instancing or simplified representations.
- Collision and gameplay data must be loadable separately from high-resolution visuals.
- GPU and CPU memory budgets must be enforced.
- Teleportation and rapid travel must not create unbounded generation queues.
- Pending generation jobs must support cancellation or invalidation.

Target smooth 60 FPS gameplay on the supported desktop performance profile and 30 FPS on supported mobile devices.

Exact frame-time, memory, streaming and network budgets must be established from the initial benchmark suite before implementation.

The new terrain system must not introduce significant regressions compared with the existing world renderer.

# 6. Settlement System 2.0

## 6.1 Objective

Remove RMB as a mandatory foundation for settlement generation.

Support three settlement sources:

**Legacy:** existing RMB settlements.

**Procedural:** new settlements generated from environmental and cultural rules.

**Authored:** custom settlements designed manually by developers.

A single settlement may combine all three approaches.

## 6.2 Settlement Placement

Generate settlement candidates using:

- Terrain slope.
- Water availability.
- Soil fertility.
- Access to resources.
- Road connectivity.
- Defensibility.
- Climate.
- Regional culture.
- Economic opportunities.
- Existing settlement density.

Different settlement types must use different suitability models.

Examples:

- Fishing villages favor coastlines and navigable rivers.
- Farming villages favor fertile land.
- Mining towns favor mineral deposits.
- Fortresses favor defensible terrain.
- Trade cities favor road intersections and ports.

Important lore-defined settlements must use authored locations rather than random placement.

## 6.3 Settlement Hierarchy

Support multiple settlement categories:

- Farms and isolated homesteads.
- Hamlets.
- Villages.
- Towns.
- Cities.
- Major capitals.
- Fortresses.
- Monasteries and temples.
- Ports.
- Specialized settlements.

Each category defines requirements for population capacity, infrastructure and services.

Do not use a single layout algorithm for all settlement types.

## 6.4 Procedural Settlement Layout

Inspired by Starchitect's general approach, settlement generation must work hierarchically.

### Stage A — Site selection

Select a suitable area and define the settlement footprint.

### Stage B — Infrastructure

Generate main access roads, settlement entrances, central spaces and infrastructure corridors.

### Stage C — Districts

Allocate areas for residential, commercial, religious, military, industrial and other purposes.

Districts must be optional and settlement-type dependent.

### Stage D — Local streets

Generate secondary streets, alleys, courtyards, paths and pedestrian access.

### Stage E — Building plots

Allocate individual building sites with valid access and terrain suitability.

### Stage F — Building placement

Select buildings based on district purpose, culture, available space and terrain.

### Stage G — Environmental integration

Add gardens, farms, trees, fences, walls, wells, markets and other local features.

The system must avoid repetitive square-grid layouts.

Roads and buildings must follow local topography wherever appropriate.

## 6.5 Terrain Adaptation

Settlement generation must interact with the terrain system.

Support:

- Foundations.
- Terracing.
- Local terrain leveling.
- Retaining walls.
- Stairs and ramps.
- Bridges.
- Elevated walkways.
- Platforms.
- Excavated areas.
- Harbors and docks.

Terrain modifications must be part of settlement data and must be reproducible.

A settlement must not generate floating buildings or buildings buried in terrain.

## 6.6 Cultural Architecture

Introduce data-driven architectural styles.

Each style defines:

- Building materials.
- Roof shapes.
- Building proportions.
- Decorative elements.
- Typical district arrangements.
- Street and plaza conventions.
- Environmental adaptations.

Examples:

**Hammerfell:** sandstone, courtyards, shaded streets, desert settlements.

**Skyrim:** stone and timber construction, steep roofs, mountain settlements.

**Morrowind:** volcanic architecture, distinctive towers and Great House styles.

**Valenwood:** elevated structures, tree-integrated settlements and canopy connections.

**Black Marsh:** raised settlements, boardwalks and structures adapted to wetlands.

These must be more than texture replacements. Different cultures must be able to use different settlement geometry and layout rules.

## 6.7 Building System

Introduce a building abstraction independent of RMB.

Each building must have:

- A persistent identity.
- A transform and spatial footprint.
- Exterior assets.
- Collision geometry.
- Entrances and exits.
- Optional interior definition.
- Building category.
- Gameplay service definitions.
- Ownership or access rules.
- Optional NPC and quest bindings.

Use component-oriented composition to share functionality without requiring a complete project-wide ECS rewrite.

A building must be able to function as an inn, shop, residence, guild hall, temple or another supported gameplay location.

Gameplay functionality must not depend on the structure being stored inside an RMB record.

## 6.8 Legacy RMB Compatibility

RMB remains supported indefinitely unless a separate, explicitly approved retirement plan is established.

Existing cities, buildings and interiors must continue working.

For legacy buildings:

- Preserve existing building keys.
- Preserve layout pins and relevant compatibility behavior.
- Maintain existing housing and interior data.
- Provide a stable mapping to the new building abstraction.

New buildings use independent persistent IDs.

Migration must never reinterpret an existing building key as a different property.

# 7. World Editor

## 7.1 General Requirements

Develop a visual editor integrated with the DFO toolchain.

It must allow developers and authorized world designers to modify terrain, infrastructure and settlements without manually editing JavaScript source files.

The preferred initial implementation is a browser-based development tool sharing the game's rendering and world-data modules.

The editor must support importing existing world data and exporting versioned content packages.

## 7.2 Terrain Editing

Implement tools for:

- Terrain raising and lowering.
- Terrain smoothing.
- Flattening.
- Noise and geological detail painting.
- Erosion operations.
- Terrain material painting.
- Biome painting.
- Rock and vegetation placement.
- River and lake editing.
- Road and trail creation.
- Cliff and canyon creation.
- Terrain masks and exclusion zones.

Brushes should support size, strength, falloff and optional masks.

Support both 3D terrain editing and top-down geographical editing.

## 7.3 Infrastructure Editing

Provide tools for creating and editing:

- Road splines.
- Paths.
- Bridges.
- Tunnels and passes.
- City walls.
- Gates.
- Harbors.
- Canals.
- Platforms and retaining structures.

Infrastructure must be able to modify underlying terrain through explicit, previewable operations.

Connected systems must be revalidated when geometry changes.

## 7.4 Settlement Editing

The editor must allow designers to:

- Create and remove settlements.
- Define settlement footprints.
- Generate settlements from selected rules.
- Edit district boundaries.
- Move, rotate and replace buildings.
- Add custom prefabs.
- Edit streets and plazas.
- Define entrances and interiors.
- Configure building services.
- Configure NPC placements.
- Define resource and gameplay areas.
- Override procedurally generated features.

Generated layouts must remain manually editable.

A designer must be able to regenerate a selected district without regenerating the entire settlement.

## 7.5 Procedural Editing Controls

Expose generation parameters through the editor.

Examples:

- Settlement density.
- Road complexity.
- Building spacing.
- District composition.
- Vegetation density.
- Terrain ruggedness.
- Erosion intensity.
- River branching.
- Biome transition widths.
- Architectural style weights.

Settings must support deterministic preview using explicit seeds.

Generated content must remain reproducible after publication.

## 7.6 Non-destructive Editing

All editor modifications must be stored as versioned data.

Requirements:

- Undo and redo.
- Named editing layers.
- Change previews.
- Revision history.
- Diff inspection.
- Validation before publication.
- Rollback.
- Selective regeneration.
- Conflict detection.

Do not overwrite or permanently destroy the underlying generated world.

An edit that changes terrain geometry must invalidate relevant downstream data, including collision, navigation, water and object placement.

## 7.7 Authoring and Publishing Workflow

Separate four states:

1. **Draft:** local changes visible only to the author.
2. **Review:** changes available to reviewers and validation tools.
3. **Staging:** changes tested in a multiplayer-compatible environment.
4. **Published:** approved changes delivered as a versioned world revision.

Published changes must be atomic at the required affected-region scope.

Partial publication must not leave a road, building or player property dependent on missing terrain data.

Direct production editing must not be the default workflow.

## 7.8 Artist Asset Pipeline

The editor must support reusable asset prefabs.

Provide a documented path for importing custom 3D assets, including glTF-compatible assets where appropriate.

Each prefab must be able to define:

- Geometry and materials.
- Collision representation.
- LOD variants.
- Placement bounds.
- Pivot and scale.
- Environmental placement rules.
- Gameplay sockets and interaction points.
- Asset ownership and licensing metadata.

Validate geometry, dimensions, material usage and performance budgets during import.

Artists must be able to create buildings, structures, vegetation and landmarks without changing the terrain renderer.

# 8. Persistent World and Multiplayer Integration

## 8.1 Server Authority

The server must be authoritative for published world revisions and persistent modifications.

Clients may generate visual details locally but cannot authoritatively change:

- Terrain collision.
- Building existence.
- Property ownership.
- Persistent resource placement.
- Navigation restrictions.
- Interactable object identities.

All clients must receive compatible world revision information before using affected gameplay geometry.

The implementation must reuse the existing relay, account service and world data infrastructure wherever practical.

## 8.2 Persistent Object Identity

Persistent entities must not be identified solely by rendering chunk coordinates or RMB record positions.

Define persistent IDs for:

- Buildings.
- Building entrances.
- Interiors.
- Settlement districts.
- Infrastructure structures.
- Resource sites.
- Authored world objects.

Legacy identifiers must be preserved through explicit mappings.

Deleting or moving a building in the editor must not silently transfer ownership or saved content to another building.

## 8.3 Existing Player Property

Before publishing world edits, validate:

- Player-owned houses.
- Interiors and containers.
- Decorations.
- Yards.
- Stored items.
- Recall locations.
- Quest destinations.
- Rental locations.
- Other persistent building-linked records.

If a world edit affects protected property, the editor must identify the conflict.

Default behavior: **reject publication until the conflict is resolved**.

Relocation or migration must require an explicit mapping, validation and rollback strategy.

No migration may silently delete player property.

## 8.4 Navigation and Collision

World edits must update:

- Client collision geometry.
- Server-side movement and collision validation.
- NPC navigation.
- Enemy pathfinding.
- Road connectivity.
- Water navigation where relevant.
- Interior and exterior transitions.

Navigation updates should be scoped to affected areas rather than rebuilding the entire continent.

Use hierarchical pathfinding for long-distance navigation and local navigation data for detailed movement.

## 8.5 Resource and Economy Integration

Generated resources should be derived from environmental information.

Examples:

- Ore distribution from geology.
- Wood availability from vegetation.
- Fishing opportunities from water bodies.
- Agricultural productivity from soil.
- Settlement industries from nearby resources.

Resource positions and gameplay ownership must remain stable across sessions.

The economic effects of generated resources must remain controlled by existing server-authoritative gameplay rules.

# 9. Data Storage and World Revisions

## 9.1 World Manifest

Introduce a versioned World Manifest describing the active configuration.

Suggested fields:

```json
{
  "worldId": "tamriel-main",
  "schemaVersion": 2,
  "geographyVersion": "geo-001",
  "generatorVersion": "wg2-001",
  "environmentVersion": "env-001",
  "authoredRevision": "edit-001",
  "settlementRevision": "settle-001",
  "worldSeed": 123456
}
```

This is an illustrative contract, not a mandatory final schema.

Exact types, hashes, compatibility rules and revision resolution must be defined before implementation.

## 9.2 Data Representation

Use different representations according to data type:

- Raster or multiresolution fields for elevation, climate, soil and other continuous data.
- Vector features for rivers, roads and boundaries.
- Entity records for settlements, buildings and landmarks.
- Spatially indexed patches for local terrain edits.
- Database records for persistent multiplayer state.

Do not store everything as one giant JSON file.

Avoid duplicating existing game data.

The existing `landEdits.json` mechanism should remain a supported coarse editing layer, while finer terrain modifications use an appropriately scalable representation.

## 9.3 Generation Versus Persistence

Separate generated state from persistent state.

Generated content can be recreated from its versioned inputs.

Persistent player-created or gameplay-created changes must be stored independently.

Updating a world generator must not automatically rewrite previously published regions.

Introduce explicit region migration or rebake operations.

# 10. World Generation Toolchain

Provide an offline or development-side generation toolchain.

The toolchain must support:

1. Importing and validating canonical geography.
2. Generating geological and erosion data.
3. Calculating drainage and hydrology.
4. Generating environmental fields.
5. Building ecosystem distributions.
6. Selecting settlement candidates.
7. Generating settlement layouts.
8. Applying authored overrides.
9. Validating world consistency.
10. Baking and exporting streamable runtime data.

The toolchain should be executable without launching the full game.

Every stage must be independently testable.

Partial regeneration must be supported.

For example, changing vegetation rules must not require recomputing continental geology.

Changing a river may require recalculating local soil, vegetation, road crossings and settlement suitability, but must not force an unrelated province to regenerate.

Implement dependency-aware invalidation.

# 11. Compatibility and Legal Requirements

The project must remain compatible with the current DFO runtime.

Do not replace the renderer, client framework or networking infrastructure as part of this task.

Maintain compatibility with:

- Original Daggerfall locations.
- RMB/RDB formats.
- Existing interiors.
- Player housing.
- Guild ownership and settlement mechanics.
- Quests and NPCs.
- Fast travel and world navigation.
- Existing mod integrations.
- Browser and desktop deployments.

All new art and generated world data intended for distribution must have documented provenance and appropriate usage rights.

Do not bundle or export protected Bethesda game data as supposedly original generated assets.

The implementation may learn from Star Citizen's publicly described design principles, but must not depend on proprietary Star Citizen code or content.

# 12. Development Phases

## Phase 0 — Architecture Audit and Canon

Before implementing major new systems:

- Audit the existing terrain and settlement pipelines.
- Document data ownership and dependencies.
- Identify source-of-truth conflicts.
- Establish performance baselines.
- Document legacy persistence risks.
- Define new interface contracts.
- Create an architecture decision record for each major design choice.

Produce a persistent project canon documenting the new world architecture, data formats, invariants and compatibility rules.

Future development agents must consult this canon.

**Exit criteria:** architecture approved, integration points identified, baseline metrics recorded.

## Phase 1 — Unified Environmental Foundation

Implement the shared environmental data model.

Integrate geology, terrain, hydrology, climate and soils through common query interfaces.

Build an isolated prototype without replacing production terrain.

**Exit criteria:** all environmental systems can query the same consistent terrain and world data.

## Phase 2 — Terrain Generation Prototype

Create a representative Hammerfell test region featuring:

- Mountain foothills.
- A connected mountain range.
- A river valley.
- A desert basin.
- Dunes.
- An oasis.
- Distinct vegetation distributions.

Demonstrate geology-driven terrain and erosion.

Include an additional wetland test site to validate low-gradient drainage and waterlogged terrain.

**Exit criteria:** deterministic, believable terrain, functional hydrology and correct streaming.

## Phase 3 — Settlement Generation Prototype

Generate several contrasting settlements within the test environments:

- An oasis village.
- A mining settlement.
- A fortified mountain town.
- A river trade settlement.
- A wetland settlement using elevated infrastructure.

Validate terrain adaptation, building access and road connectivity.

**Exit criteria:** settlements function without mandatory RMB blocks and support gameplay-relevant building metadata.

## Phase 4 — World Editor

Implement the visual editing tools.

Start with terrain brushes, road splines, object placement and prefab management.

Add settlement editing, validation and publishing tools.

**Exit criteria:** a designer can generate, customize, save, reload and publish a new playable settlement without writing application code.

## Phase 5 — Gameplay Integration

Integrate:

- Building services.
- Housing compatibility.
- NPC navigation.
- Resource placement.
- Quest locations.
- Economy hooks.
- Multiplayer revision synchronization.

**Exit criteria:** generated settlements operate as functional DFO settlements, not merely visual scenery.

## Phase 6 — Controlled Production Migration

Introduce the system progressively.

Start with new or unoccupied regions.

Preserve existing locations unless explicit migration is approved.

Compare new terrain streaming and gameplay behavior against existing production.

**Exit criteria:** stable multiplayer operation, validated player data compatibility and an independently tested rollback procedure.

## Phase 7 — World Expansion and Production Tools

Expand the system across Tamriel.

Add province-specific generation profiles, advanced procedural architecture and a broader artist prefab library.

Optimize editor usability and regional regeneration.

**Exit criteria:** world designers can create and maintain diverse regions through data and authoring tools without routinely changing core engine code.

# 13. Validation and Acceptance Criteria

The project must include automated tests, integration tests and in-engine visual verification.

## Environmental Consistency

- Rivers must have coherent downstream connectivity.
- River surfaces must not rise upstream-to-downstream without an explicit exceptional feature.
- Terrain and water geometry must align.
- Geological features must remain continuous across chunk boundaries.
- Biome transitions must not create unintended hard seams.
- Vegetation must satisfy its declared placement constraints.
- Terrain generation must be reproducible from versioned inputs.

## Settlement Consistency

- Every accessible building must have a valid approach or entrance.
- Buildings must not float or become unintentionally buried.
- Roads must connect required settlement destinations.
- Structural terrain modifications must be reproducible.
- Custom settlements must work without RMB.
- RMB settlements must continue to function.

## Persistence and Multiplayer

- Two clients on the same revision must agree on gameplay terrain and settlement identities.
- World edits must not silently remove or reassign existing houses.
- Persistent containers and decorations must remain attached to their intended owners and structures.
- Existing saves and active online characters must remain valid.
- Navigation and collision must agree with the published world revision.
- Older clients must not silently accept incompatible revisions.

## Editor Reliability

- Save and reload must reproduce the edited world.
- Undo and redo must preserve data integrity.
- Invalid edits must be rejected with actionable explanations.
- Publishing must be atomic.
- Rollback must restore the previous revision.
- Partial regeneration must preserve unrelated authored modifications.

## Performance

- No expensive continental simulation during normal gameplay.
- No long synchronous terrain-generation tasks on the main rendering thread.
- Bounded memory usage and streaming queues.
- Stable LOD behavior.
- No significant regression against measured baseline performance.
- No uncontrolled network transfers of unmodified generated terrain.

All acceptance tests must run on representative low, medium and high graphical settings, with browser performance measured separately from server performance.

# 15. Non-Goals

The initial implementation does not require:

- Real-time continental tectonic simulation.
- Physically exact geological simulation.
- Real-time regional erosion.
- Unrestricted terrain editing by ordinary players.
- Replacing all existing RMB towns.
- A new rendering engine.
- A new networking architecture.
- A complete rewrite of existing gameplay systems.
- Automatic regeneration of the entire persistent world after every update.

These are not prerequisites for achieving believable environments and diverse settlements.

# 16. Final Architectural Requirements

The following principles are non-negotiable:

**1. One coherent world.** Terrain, water, vegetation, infrastructure and settlements must share compatible environmental information.

**2. Data-driven generation.** Designers must be able to create new regional rules and settlement styles without repeatedly modifying engine logic.

**3. Procedural plus authored.** Procedural generation provides scale; manual editing provides quality, landmarks and artistic direction.

**4. RMB compatibility without RMB dependency.** The old world continues working, while the new world can use unrestricted geometry.

**5. Multiplayer determinism.** Gameplay-relevant geometry and persistent identities must be consistent across all players.

**6. Protected persistence.** No world regeneration or editing operation may silently corrupt persistent player data.

**7. Browser-first performance.** Expensive world creation should happen before runtime; the client should primarily stream, reconstruct and render efficiently.

**8. Incremental migration.** Existing systems must be extended and integrated before considering replacement.

**9. Production-ready authoring.** The World Editor is a core system, not a demonstration tool or optional late-stage feature.

**10. Scalable world design.** The architecture must support the entirety of Tamriel without assuming that all content can be loaded, generated or simulated simultaneously.

## Definition of Done

The project is complete when DFO can generate geographically coherent terrain, build culturally distinct settlements on that terrain, allow designers to modify both through a visual editor, publish those changes safely to a persistent multiplayer world, and retain full compatibility with existing player data and legacy locations.

**The ultimate goal is not merely better procedural generation. It is a unified, editable, persistent world-building platform capable of supporting DFO's long-term expansion across Tamriel.**
